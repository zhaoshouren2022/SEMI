# FAQ：高频疑问答疑

> 学习 `SECS-II`（`E5`）过程中的高频疑问，按主题归类，答案标注标准出处。附录 R1 的建议（消息选择、基线实现）也集中放在这里。

## 1. 概念与编号

**Q1: `SxFy` 的编号到底怎么来的？`S1F13` 里的 `1` 和 `13` 分别是什么？**

- `S` 后面是流号（`Stream`，7 位，0-127），`F` 后面是功能号（`Function`，8 位，0-255）。`S1F13` = 流 1 功能 13（§7.1、§7.2）。
- 流按"活动类别"分（状态、控制、数据采集…），功能是流内具体消息。
- **主消息用奇函数号**，回复 = 主消息 + 1（偶）。`S1F13` 的回复就是 `S1F14`（§7.2）。

**Q2: 为什么主消息是奇数、回复是偶数？**

这是 §7.2 的编号约定：`Primary`（主）奇、`Reply`（次）偶，接收方看到函数号奇偶就知道"这是请求还是回复"，不需要额外标志。主消息若声明不要回复，紧邻的偶数号**保留不用**。

**Q3: `Stream 0` 为什么不存在？函数 0 有什么用？**

- 流 0 定义为"未使用"——`0` 是最可能的错误值，不能再承载功能（§10.4）。
- 函数 0 在**所有流**中含义相同：解释方无法给出期待的回复时，用它**关闭事务**，让发起方不必等到事务超时（§10.4.1）。它不是必须发的。

**Q4: 244 字节是什么？为什么消息还要分块？**

- 244 字节是 `SECS-I`（`E4`）兼容的**单块最大长度**（§6.3.1）。`SECS-II` 本身不限制消息长度，超过 244 字节的称为**多块消息**（§6.3.2）。
- 标准要求传输协议**至少能发单块消息**；多块不是必须支持的（但支持的消息若定义要求单块，则必须单块发）。
- 某些多块发送（如 `S2F23`、`S2F33`）必须先走 `Inquire/Grant` 事务取得许可。

**Q5: `Item` 和 `List` 有什么区别？**

- `Item` 是一段实际数据（带格式码 + 长度，自描述）；`List` 是一组元素（元素可以是 `Item` 或 `List`）的有序集合（§9.2、§9.3）。
- `Item` 头的长度指**数据体字节数**；`List` 头的长度指**元素个数**。
- 消息最外层通常是一个 `List`，内部嵌套形成树状结构。

**Q6: `SECS-II` 的格式码为什么是八进制编号（`10`、`20`、`30`…）？**

因为格式码实际是格式字节的 `bit` 3-8（6 位），标准按八进制分组好记：`00` `List`、`10` 二进制、`20` `ASCII`、`30` 有符号整数、`40` 浮点、`50` 无符号整数。`31`/`32`/`34` 表示 1/2/4 字节整数（§9.2.2 表 1）。

## 2. 事务与对话

**Q7: "事务"和"对话"到底差在哪？**

- **事务（`Transaction`）**：一条主消息 + 其回复（如果有）——最小交换单元（§8.2）。
- **对话（`Conversation`）**：完成一个任务的一组相关事务（§8.4），比如"询问许可→发多块数据→确认"。
- 一句话：事务是"一次一来一回"，对话是"一组配合"。

**Q8: 多块发送为什么要先 `Inquire/Grant`？不先问行不行？**

对需要多块的消息（如 `S2F23`、`S2F33`、`S2F41`），标准要求先走 `Inquire/Grant`（`SxF39/SxF40` 之类）取得许可（§6.3 各处、§8.4.2 对话 ④）。许可让解释方**预留资源**，避免接收方被超大数据淹没。`S6F1`（`Trace` 数据）是例外——`S2F23` 本身是隐式许可，多块 `S6F1` 不需要再问。

**Q9: 事务超时和对话超时分别发什么？**

- 事务超时（§6.5）：设备向主机发 **`S9F9`**（§8.3 要求 4）。
- 对话超时（§8.4.1）：设备向主机发 **`S9F13`**。
- 收到函数 0 回复时**不发**错误消息，直接终止事务（§8.3 要求 5）。

**Q10: 设备收到的消息无法处理时怎么办？**

按错误类型发对应 `S9` 消息：`S9F1`（未知 `Device ID`）、`S9F3`（未知流）、`S9F5`（未知功能）、`S9F7`（非法数据）、`S9F11`（数据过长）（§10.13）。这是最小合规的第二条要求。

## 3. 常用消息

**Q11: `S1F13/S1F14` 建立通信里到底传什么？**

- `S1F13`：`L,2`：`<MDLN>`（型号）+ `<SOFTREV>`（软件版本）——设备宣告"我上线了，我是谁"。
- `S1F14`：`L,2`：`<COMMACK>`（`0` = 接受）+ `L,2`（`MDLN` + `SOFTREV`，仅在 `COMMACK=0` 时有效）。
- 设备应**按可编程间隔重复** `S1F13`，直到收到接受的 `S1F14`（§10.5）。这是 `E30` 通信状态机的消息基础。

**Q12: `S2F41`（`Host Command`）和 `S2F21`（`Remote Command`）有什么区别？**

- `S2F21`：`<RCMD>` 单个命令名，类似按面板按钮（§10.6）。
- `S2F41`：`RCMD` + **参数列表**（`CPNAME`/`CPVAL` 对），更强大；`E30` 的 `START`/`STOP`/`PAUSE` 等带参数的远程命令走这条（[E30 远程控制](../e30/remote-control.md)）。
- `S2F49`（`Enhanced Remote Command`）是 `S2F41` 的增强版（多块时先 `S2F39/S2F40`）。

**Q13: `S6F11` 事件报告和 `S6F1` `Trace` 数据有什么区别？**

| | `S6F11` 事件报告 | `S6F1` `Trace` 数据 |
| --- | --- | --- |
| 触发 | 事件（`CEID`） | 时间采样 |
| 配置 | `S2F33`+`S2F35`+`S2F37` | `S2F23` |
| 结构 | `DATAID`+`CEID`+报告列表 | `TRID`+`SMPLN`+`STIME`+值列表 |

一个"发生了什么就报什么"，一个"按时钟周期采数据"（§10.10、附录 `R1-3`）。

**Q14: `S6F11` 和 `S6F13` 都是事件报告，差在哪？**

`S6F13`（`Annotated Event Report`）每个值前带 `VID`（变量 ID），自描述更强；`S6F11` 只按顺序放值（§10.10）。报告结构固定时用 `S6F11`，需要标识每个值时用 `S6F13`。

## 4. 数据与格式

**Q15: 零长度 `Item`/`List` 是什么意思？**

消息定义允许时（§10.3.1）：对命令/请求 = "用默认值"；对数据上报 = "信息不可用/不适用"；也可 = "信息未提供"。**注意**：只有消息定义明确给出含义时才允许零长度（§10.3.2）——不能随便用。

**Q16: `S1F3` 请求状态变量为什么有两种结构？**

新结构 `L,n`（每个 `SVID` 一个项）适用于所有格式；旧结构 `<SVID1,...,SVIDn>`（多项合一）**只能用于 `3()`/`5()` 格式**（整数类），为兼容旧实现保留（§10.5）。新实现用新结构。

**Q17: 状态变量值（`SV`）、常数值（`ECV`）、报告值（`V`）的格式是固定的吗？**

不固定。这些"值"项的格式**由对应的 ID 决定**（`SVID`/`ECID`/`VID` 定义它是什么类型），数据项字典里用"按 ID 引用"标注（§9.6）。所以主机必须知道设备每个 `SVID` 的类型才能解析 `S1F4`。

**Q18: `TIME` 时间格式长什么样？**

`S2F18` 返回 `<TIME>`：`YYYYMMDDHHMMSS` 的 `ASCII` 串（§10.6）。`GEM` 时钟同步（`S2F17/F18`）和 `S2F31/F32`（设时间）都用它。

## 5. 工程实践（附录 R1）

**Q19: 我的设备最少要实现哪些消息？（§8.3 + 附录 `R1-5`）**

**必须**：收到 `S1F1` 回 `S1F2`；设备生成 `S1F2`、`S9F1`/`F3`/`F5`/`F7`；事务超时发 `S9F9`（§8.3）。

**强烈建议**（`R1-5.6.2`）：`S2F25/F26`（字符串诊断回环）、`S10F1/F3`（终端）。

**按设备类型建议**（`R1-5.6.4`，节选）：

| 任务 | 建议消息 |
| --- | --- |
| 测量/动作上报 | `S6F3`（离散变量）、`S6F9`（格式化变量） |
| 设备报警上报 | `S5F1`（报警报告） |
| 远程请求设备状态 | `S6F7/F8`（数据传输） |
| 操作员界面 | `S10F1`（终端请求）、`S10F3`（终端显示） |
| 远程访问工艺程序 | `S7F1-F4`（加载询问/许可/发送/确认）、`S7F5/F6`（请求/数据） |
| 远程命令 | `S2F21/F22`（远程命令） |
| 物料状态/传输 | `S3` 系列、`S4` 系列、`S1F9/F10`（端口状态） |

**Q20: 设备厂商该不该把所有流都实现？**

**不该**。`SECS-II` 最小合规很低（§3.1.1），"消息数量与选择取决于设备能力与需求"（§3.1.1、`R1-5`）。简单测量设备可能只需要 `S1F1/F2` + `S6F9`；复杂设备才需要 `S4`/`S7`/`S13` 等。选择消息集时要考虑设备任务与主机系统要求（`R1-5.4.3`）。

**Q21: 附录 `R1-1`（`General Node Transaction Protocol`）在哪？**

该应用笔记已移入 `SEMI E4`（`SECS-I`）的附录 A7（`R1-1`.1）。`R1-2`（消息用法建议）、`R1-3`（数据传输笔记）、`R1-4`（工艺程序）、`R1-5`（基线实现）仍在本标准附录中。

**Q22: 我的设备要不要实现 `Spooling`？**

`Spooling`（通信中断时缓冲消息、恢复后补发）是 `E30` 的**附加能力**（`MaxSpoolTransmit`、`OverWriteSpool` 等设备常数控制它），消息层面由 `S2F43/F44`（选择要 `Spool` 的流/功能）与 `S6F23/F24`（请求缓冲数据）实现（§10.6、§10.10）。**`Stream 1` 不允许 `Spool`**（§10.6 `S2F43` 注 2）。

## 6. 与其他标准的关系

**Q23: `E5` 和 `E30` 是什么关系？会不会重复？**

- **`E5`** 定义消息的"形状"（结构、数据项、格式码）；**`E30`** 定义"什么时候发、设备要做什么"（行为层）。
- 同一个 `S6F11`：`E5` 定义它的 `L,3` 结构（`DATAID`+`CEID`+报告列表），`E30` 定义"事件发生后设备自动上报"这个行为。
- 所以两份标准是**互补**的，不是重复（详见 [E30 总览](../e30/index.md)）。

**Q24: `SECS-II` 消息在 `HSMS` 上怎么传输？**

消息内容完全不变，只是传输层的"壳"变了：`HSMS` 用 4 字节长度 + 10 字节头部（`Session ID`、`PType`、`SType`、`System Bytes`）+ 文本，`PType=0` 表示文本是 `SECS-II` 编码（[E37 消息格式](../e37-hsms/message-format.md)）。`SECS-II` 的 `Device ID` 对应 `HSMS` 的 `Session ID` 低 15 位（`HSMS-SS`）。

**Q25: `S7` 工艺程序和 `S15` 配方管理有什么区别？**

- `S7` 是传统"工艺程序"管理（`PPID` + `PPBODY`，设备特定描述），`GEM` 时代的主流。
- `S15` 是对象化"配方"管理（命名空间、属性、分段传输、`DRNS` 变更管理），更通用、更现代。
- 两者都做"下载/上传/验证/选择/删除"，但 `S15` 增加了命名空间与变更管理机制（§10.11、§10.19）。
