# FAQ：E30 学习常见疑问

> 高频疑问按主题归类，答案标注标准出处。学习顺序建议见[总览](index.md)。

## 一、E30 与 E5 / E4 / E37 的关系

**Q1：E30 和 E5（SECS-II）到底什么关系？**

E5 定义"消息长什么样"（S1F13 的消息结构、COMMACK 的取值、数据项格式）；E30 定义"什么时候用哪个消息、设备该有什么行为"。同一消息在两份标准里分工不同：E5 给定义，E30 给使用规则（§1.2 Scope："GEM defines which SECS-II messages should be used, in what situations, and what the resulting activity should be"）。

**Q2：GEM 是不是必须用 HSMS？**

不是。E30 明确说能力与底层传输协议无关（§1.2）：SECS-I（E4）、SMS（E13）、HSMS（E37）都可以，标准"不要求也不排除"任何一种。E30 里的"通信失败"定义直接转交传输层标准（§3.2.1、§4.9.3）。

**Q3：E30 定义了主机行为吗？**

不定义。主机可以随时发起任何 GEM 场景，设备必须按标准响应（§1.2）。GEM 视角是"从通信链路往里看的设备黑盒"。

## 二、状态模型

**Q4：通信状态模型里的"通信"是物理链路还是逻辑的？**

逻辑的。S1F13/F14 成功完成（COMMACK=0）即"建立通信"，与底层 TCP/串口是否连着一个概念（§3.2.1、§3.2.4）。NOT COMMUNICATING 时物理链路可能好好的，只是 GEM 层面还没"正式建立"。

**Q5：NOT COMMUNICATING 状态能收发什么消息？**

只允许 S1F13、S1F14 和 S9Fx；收到其他消息直接丢弃（§3.2.4）。设备会周期重发 S1F13（间隔 = `EstablishCommunicationsTimeout`）直到建立通信。

**Q6：控制状态的三档（REMOTE/LOCAL/OFF-LINE）有什么区别？**

REMOTE：主机全权；LOCAL：信息全通但禁止引起物理移动/启动加工的远程命令；OFF-LINE：只响应 S1F13/S1F17，对其他主消息回 Sx,F0（§3.3）。

**Q7：操作员和主机谁能切控制状态？**

操作员：切 OFF-LINE（OFF-LINE 键，终极权限）、发起上线（ON-LINE 键 → 设备发 S1F1）、切 LOCAL/REMOTE。主机：S1F15 请求下线、S1F17 请求上线（仅当 HOST OFF-LINE 活跃时接受）。只有操作员能切 LOCAL/REMOTE（§4.12.3.2）。

**Q8：加工状态模型是强制的吗？**

具体状态不强制——E30 只给示例模型（§3.4），但要求：① 厂商文档化自己的加工状态模型；② 每个状态迁移都产生采集事件；③ 提供 `ProcessState` / `PreviousProcessState` 状态变量。

## 三、数据采集与事件

**Q9：事件报告和报警消息有什么关系？**

两条独立通道，都可能在报警时发：S5F1/2 是固定格式的简要报警消息；S6F11 事件报告可以挂任意扩展数据。都使能时**报警消息必须先发**（§4.3.3.2）。使能/禁用 S5 报警会成对影响两条通道，但事件通道里 set/cleared 两个 CEID 可分别使能（§4.3.3.1）。

**Q10：报告（Report）、事件（CEID）、变量（VID）的关系？**

变量（VID）组成报告（RPTID）；报告挂接到事件（CEID）；事件使能后发生即上报。三步配置：S2F33 定义报告 → S2F35 链接 → S2F37 使能（见[事件通知](event-reporting.md)）。

**Q11：Trace 和事件报告有什么区别？**

事件是"发生了才报"（异步），Trace 是"按固定间隔采样"（周期，S2F23 定义 DSPER/TOTSMP/REPGSZ 后设备自己跑）。Trace 至少 4 路并发（§4.2.3.4）。

**Q12：Limits 监控的"死区"是干什么的？**

防止变量在边界附近抖动导致反复换区（chattering）：值必须到达死区另一侧边界才算换区。如 UPPERDB=LOWERDB=100 时，99→101 换区，101→100 又换区（§4.2.4.3.1 示例）。

**Q13：事件报告里的数据一定是当前值吗？**

是。事件发生时报告必须即时构建（§4.2.1.1.3）。DVVAL 只在特定事件/状态下保证有效，厂商需文档化（§4.2.1.2.4）。

## 四、通信与故障

**Q14：为什么建立通信不用 S1F1/F2？**

S1F1/F2 用途宽泛、随时可用，语义不明确。S1F13/F14 专门表达"我们之间有过无法通信的时期，请重新同步"（§4.1.1）。

**Q15：S9 流是不是都要支持？**

是，S9F1~F13 全部必须支持（§4.9.4）——未识别设备 ID/流/功能、非法数据格式、事务超时、数据过长、会话超时。

**Q16：E30 里的"通信失败"和 E37 的 T 系列定时器怎么对应？**

E30 把"通信失败/回复超时"的定义转交传输层标准（§3.2.1 注释、§4.9.3）：SECS-I 看 E4，HSMS 看 E37。E30 自己的 `EstablishCommunicationsTimeout`（S1F13 重试间隔）和 `MaxSpoolTransmit` 等是应用层常数，与 E37 的 T3/T5… 不是一回事。

## 五、工艺程序与配方

**Q17：工艺程序和配方有什么区别？**

工艺程序（S7）是加工指令集；配方（S15）= 工艺程序体 + 属性，GEM 语境特指 E42 执行配方（§4.6.2.2）。同名覆盖策略不同：PP 同名直接替换；配方同名默认拒绝，除非 `RCPOWCODE=TRUE` 强制覆盖。

**Q18：大文件怎么传？**

走 Stream 13 数据集传输协议（S13F1~F8）：打开数据集 → 循环 Read 直到 "ERROR: END OF DATA" → 关闭。配合 S7F37~44 / S15F49~54 的大文件功能，无大小上限（§4.6.3.3）。

**Q19：验证（Verification）和校验（Validation）有什么不同？**

验证 = 语法/结构检查（下载后必须做，§4.6.2.1）；校验 = 类型/范围检查（选择执行时做）。验证通过 ≠ 能跑，参数不对会在校验阶段暴露。

## 六、其他

**Q20：Spooling 能存哪些消息？**

只存用户通过 S2F43/44 选择的流/功能的主消息，Stream 1 消息（S1F1、S1F13 等）永远不 Spool；副消息不 Spool，发不出就丢弃（§4.11.3.1、§4.11.4）。

**Q21：通信恢复后 Spool 数据会自动发给主机吗？**

不会。必须由主机发 **S6F23**（RSDC=0 发送 / 1 丢弃）取回（§4.11.3.1）。发送按最旧优先、一次一个打开事务、受 `MaxSpoolTransmit` 限制。

**Q22：E30 和 E30.1 / E30.5 是什么关系？**

E30 是通用母标准；E30.1（ISEM，检测/复查设备）和 E30.5（MSEM，计量设备）是**专用设备模型**，在 E30 之上补充本类设备的专用状态模型、事件、命令、数据项。它们不是 E30 的旧版本，详见[总览](index.md)第 4 节。

**Q23：怎么判断一台设备算不算"GEM 设备"？**

看 §8.3：基础要求全满足 + 每项声称的能力按标准实现 + 无冲突行为 = 该项合规；全部附加能力都实现且合规 = **Fully GEM Capable**。厂商应提供合规声明表（表 8.3）。
